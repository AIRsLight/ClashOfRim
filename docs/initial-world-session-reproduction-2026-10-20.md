# 首次建世界后未进入多人会话：定向复现记录

用户报告：首个管理员创建世界后立即建立殖民地，进入地图后没有多人按钮和多人菜单；恢复游戏运行仍未连接。世界信息第一次就已保存，再次进入后殖民地也被保存。

**截至本轮，尚未复现“持续运行仍无多人会话”的完整故障。** 已复现一个相关但不同的时序问题：初次建图资料提交尚未完成时运行一段游戏，随后暂停，提交完成后不会自动启动地图会话；再次推进游戏后可以连接。不能据此把用户报告归因于暂停。

## 测试输入和边界

- 本地 Steam RimWorld `1.7.4980 rev60`。
- 客户端使用已发布 `0.4.1-dev.76e4c0c4` 的下载 ZIP 解压产物，未使用工作区编译的客户端。
- 新建独立服务端数据目录、新账号、独立游戏 profile；服务端通过隔离源码副本中的正常 `ClashOfRimNetworkServer.Build` 启动，HTTP loopback，非远程部署。
- 使用 Harmony、RimTest、ClashOfRim 测试桥接；内容配置分别为 Core 和全部五个官方 DLC。未加载第三方内容模组或第三方兼容包。
- 英文游戏语言、`en-US` 区域，30% 世界覆盖率、Cassandra/Peaceful、默认 Crashlanded 场景。
- 图形模式隐藏窗口，`headless=false`，`DOTNET_PROCESSOR_COUNT=4`。操作使用真实产品入口及原版页面回调，没有进行操作系统鼠标交互或多人按钮像素检查。
- 本轮只做首次加入、继续运行、退出并重进三个阶段，不运行完整业务回归。收集了日志，但三个阶段的通过不等于严格运行日志审计通过。
- 用户实际运行的客户端/服务端版本、模组组合、当次日志尚未取得，因此尚不能声称覆盖了相同环境。

## 场景与结果

每轮注册首个管理员，经 `StartMainMenuServerEntryFlow` 进入原版建图页面，生成世界、选择落点、建立殖民地。关闭原版落地叙述后推进 600 ticks，检查客户端会话与快照；随后再推进 600 ticks，最后经原版返回主菜单后重新登录。

| 配置 | 首次建殖民地 | 后续推进游戏 | 重进已保存殖民地 |
| --- | --- | --- | --- |
| Core | 通过 | 通过 | 通过 |
| 全 DLC | 通过 | 通过 | 通过 |
| 全 DLC，管理员资料要求请求延迟 20 秒 | 失败：等待期间处于暂停，未启动地图登录 | 通过：再次推进后建立会话、上传快照 | 通过 |

普通 Core 和全 DLC 两轮均观察到：

- `isInActiveMultiplayerSession=true`，`currentSnapshotId` 非空；
- 服务端已保存世界与殖民地快照，`OnlinePresence.IsUserOnline` 为真；
- 重进加载同一快照，客户端游戏实例更换后重新建立会话。

延迟轮通过测试服务端中间件，仅延迟 `GetAdminBaselineRequirements` 请求 20 秒，未修改产品代码。轨迹确认：落地并执行首批 600 ticks 时，初次世界提交仍持有同步操作；之后测试框架在有限步进结束时暂停。资料提交完成后，等待约 90 秒仍未建立会话，快照列表为空。再次推进 600 ticks 后，会话、快照和服务端在线状态均成功。

这轮的报告为 **失败**，保留原始超时，不将随后恢复改写为整轮通过。它证明暂停和提交时序有关，不能证明用户持续运行时的失败。

另外尝试启动简体中文配置，但当前 Steam 安装的 Core/Languages 只有 English，框架在启动前拒绝 `ChineseSimplified`。该尝试没有运行游戏场景，不计作通过或产品功能失败。

## 代码对应关系

- `MainButtonWorker_ClashOfRimMultiplayer.Visible` 在原版可见条件之外，要求 `ClientSessionLifecycle.HasConfiguredSession`。它检查已配置身份和非空会话 ID，不以世界文件已保存为条件。
- 多人存档菜单由 `ClientSnapshotSaving.CanUseMenu` 控制，需要会话和当前快照；`ClientSessionStartup.IsInActiveWorld` 同样需要快照会话，并排除观察地图。
- 发布版本只在 `ClashOfRimGameComponent.GameComponentTick` 调用自动会话启动。暂停期间即便 GUI 已处理完世界提交回调，也不会触发下一次自动登录尝试。
- `ClientSessionStartup.CanStartAutomatic` 会等待初次世界同步结束；资格不足不会消耗自动启动机会。因此延迟轮在提交完成后再次运行可以恢复。
- 一旦开始了自动登录尝试，当前实现不会在同一 Game 内自动重试失败。尚无本次用户日志证明实际命中了网络失败、服务端拒绝或会话失效，不能把这一代码分支当作已确认根因。
- 工作区已有一项未提交修改，把主线程队列和自动启动加入 `GameComponentUpdate`。本轮特意使用发布包绕开它；不能将工作区行为等同于发布版，也没有将该既有修改纳入本报告提交。

## 测试设施发现与解释限制

现有 `ServerEntryScenario.Enter` 先等多人会话建立，后关闭原版落地叙述。发布版在叙述强制暂停期间不触发自动登录，这会造成测试自身等待顺序错误。第一轮诊断的 0 tick 超时因此不作为用户完整故障的复现证据。

后续仅在本地探针副本中调整顺序：先关闭原版唯一的落地确认选项，再推进 ticks 和等待会话。没有模拟登录成功，也没有直接填写会话或快照字段。

还观察到玩家列表缓存短暂显示自身 Offline，但同时实际会话和服务端在线记录为真。用户明确描述多人按钮和菜单缺失，因此不能拿这条显示差异解释用户问题。
