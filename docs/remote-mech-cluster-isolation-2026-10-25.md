# 侦察机械集群结算隔离（2026-10-25）

## 已确认的原因

- NPC Lord 快照保留了 `isMechCluster`，但遗漏了原版 `mechClusterDefeated`。重新构造 LordJob 后，该值恢复为 false；源地图已经完成结算的集群因而可能再次进入战败流程。单元测试已在旧实现上复现状态丢失。
- 原版 `LordJob_MechanoidDefendBase` 的计时入口和控制器销毁入口都会调用同一个 `OnDefeat`。它不仅发出消息，还会通知集群对象、记录袭击历史、给予心情、发送 `AllEnemiesDefeated` 任务信号并播放声音。远程任务标签的命名空间隔离不能阻止这些其他效果。
- 原有关闭流程只在地图卸载阶段开启全局效果抑制；提前丢弃远程单位也可能销毁最后一个成员所属的 Lord，需要覆盖这一阶段。
- 上述为代码与定向测试确认的路径；没有用户故障发生时的存档/执行轨迹，不能据此认定那次通知实际发放了哪些任务物资。

## 修复

1. 在 NPC 快照捕获、ID 投影、延迟子地图 JSON 持久化和 LordJob 重建之间保留已击败状态。休眠、活动两类机械集群共用恢复逻辑。
2. 在原版共同战败入口判断事件所属地图：侦察、友好观察、袭击旁观及它们的嵌套子地图均不执行战败回调，同时标记完成，避免后续每 tick 重试。复用已有远程父地图识别，不依赖当前正在看的地图。
3. 实际袭击保留正常战斗结算，但处于远程清理作用域时同样禁止触发。公共单位清理入口将地图单位与引用单位清理纳入已有作用域，避免在地图卸载前触发结算。
4. 本地地图及本地子地图正常结算不受远程清理作用域影响；未改动防守方源存档、协议或冻结的 1.6。

- `RemoteMechClusterTests` 使用本机 1.7 的原版 `LordJobTick`、`Notify_LordDestroyed`、`OnDefeat`、`QuestUtility` 和 `SignalManager`。仅在 UI、音效、心情/历史写入等外部边界记录调用，不替换战败判定和信号发送算法。
- 原版正向对照确实触发全部七类记录（含对象回调和任务信号），避免把无效测试夹具误判为隔离成功。
- 覆盖两个 LordJob、已击败字段缺省/false/true、克隆与延迟存储、四种会话模式、根/子/嵌套地图、计时/销毁入口、清理/正常运行、重复完成，以及本地地图隔离。
- 模拟实际公共单位清理回调，在地图卸载前触发原版控制器销毁，确认作用域已生效并正常释放。
