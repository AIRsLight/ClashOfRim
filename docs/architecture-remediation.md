## 缺陷依据与设计约束

### 1 行为测试未进入发布门槛

`.github/workflows/release.yml` 原流程只构建与验证包。现有 Client、Save、Events 均为控制台测试程序，必须用 `dotnet run` 执行，不能用返回成功但不执行这些用例的 `dotnet test` 替代。客户端完整测试必须使用本地游戏运行库；NuGet 中的引用程序集不能执行游戏代码。

### 2 会话生命周期

`ClashOfRimMod.SessionRuntime.cs` 的普通后台刷新未统一绑定取消与代次。退出会清空集合，但旧响应随后仍可调用 `CaptureWorldMapMarkers`、`MergeChatMessages`；主线程动作也可能跨游戏实例执行。已有重连安全策略保留，新增会话所有权应覆盖结果应用与 finally 清理，防止旧请求清除新请求的运行标记。

### 3 跨存储提交

`RepayBankLoanWithSnapshot` 先 `ReceiveSnapshot`，后 `MarkRepaidWithSnapshot`。文件原子替换只保证快照文件完整，不保证与 SQLite 业务记录共同提交。中途崩溃可能留下扣钱快照和未还贷款。待确认恢复只处理已有 Pending 记录，不能推导未持久化的业务意图。改造必须有持久化意图或共同事务边界；不能只加进程内锁。

### 4 快照锁范围

`ReceiveSnapshot` 在 `RaidSettlementSnapshotMutationGate` 内执行解压、哈希、XML 索引和存储。优化必须保留提交时的连续性、lineage 和袭击结算互斥检查；不能只将原调用移出锁。存储层共用锁也需要单独评估。

### 5 职责边界

`ClashOfRimMod` 的 partial 文件共享会话、经济、世界、聊天和 UI 状态。`ClashOfRimNetworkState` 是全量依赖集合，端点直接编排持久化。优先抽出前述修复需要的真实服务，避免只重命名或移动文件。远程地图投影中的 Scribe、Current.Game 和反射调用应有独立的游戏运行时入口。

### 6 协议重复

`ClashOfRimModNetworkClient` 手写路由，`ClientNetwork/Dtos` 与 `ClashOfRim.Protocol` 同时定义传输模型。先共享路由；DTO 迁移必须保持现有 JSON 字段、枚举、可选值、默认值兼容，并以两端实际序列化器验证。1.6 冻结客户端不重新编译。

## 续修：礼物快照与事件共同恢复

首轮改动已提交为 `df3d4bfa`。本步继续解决问题 3，范围为 `CreateGiftWithSnapshot`。

- 原流程在发布扣除物品后的快照之后才保存物品包和投递事件。现改为：准备快照 → 锁内重验 lineage 与幂等键 → 持久化物品包 → 固定礼物事件 → 写入提交意图 → 发布快照 → 追加事件 → 通知及后处理 → 删除意图。写入意图之前失败可能遗留未引用物品包，但不会发布扣物品快照。物品包使用每次提交独立的命名空间，避免失败尝试复用其他请求的包。
- `BankSnapshotCommitService` 扩展为 `SnapshotCommitService`，银行与礼物共用恢复入口及快照冲突检查。礼物日志保存稳定的事件 ID、双方身份、物品来源与接收方式；恢复使用原事件，不重算当前配置。事件已追加但通知失败时，恢复再次唤醒接收者，不新增投递事件。
- 重试必须匹配发送者、殖民地、确认快照、礼物业务类型和接收者；认证主体必须匹配请求发送者。提交锁内再次检查重复请求。较新快照或已被其他事件占用的幂等键会阻止恢复，日志保留供排查。
- 为读取既有未完成银行日志，继续使用数据目录 `bank-snapshot-commits/`。银行记录仍使用格式 1，礼物使用格式 2；数据版本 9→10 要求服务端支持礼物恢复。备份仍需包含该日志目录、SQLite、快照及物品包；后处理器仍须幂等。
- 新增 7 个故障/冲突场景，使用真实 SQLite、快照文件并重新打开存储：快照前、快照后、事件写入、通知、后处理失败，以及较新快照和幂等键冲突。旧银行格式缺少 `Gift` 字段的日志也纳入恢复测试。

## 续修：交易所需的账本原子批量提交

- `IAuthoritativeEventLedger.ApplyBatch` 将新增事件与既有事件状态变更作为一批处理。SQLite 使用单个事务，文件账本先持久化完整候选集合再发布缓存，内存账本在同一锁内检查并应用；文件及内存账本其他公开操作也使用同一锁。
- 状态变更携带预期旧状态。已经关闭订单的新成交批次会被拒绝；只有整批事件已存在时，才允许按既有完成状态重试。重试保留投递事件后续的消费状态，不将其恢复为待投递。
- 新增三个账本实现的验证失败、SQL 中断回滚、文件保存失败缓存隔离、持久化重开、重复执行及并发买家竞争测试。本步骤提供基础能力；交易端点接入提交日志另作下一步，尚不能据此认定交易跨快照恢复完成。
- 验证：`Tools/Test-Regression.ps1` 通过（Events 51 项、Save 75 项、Client.Core 5 组及 NetworkSmoke 独立管线）；全部 77 个 1.6 冻结文件哈希保持不变。

## 续修：袭击证据发布意图与冲突恢复

- 原 `Prepared` 恢复只比较证据快照 ID，不同就直接安装证据，可能覆盖较新存档或复活已删除殖民地；写文件抛错时还可能删除已持久化任务和证据，丢失“文件实际已发布但调用失败”的恢复依据。
- 新任务在原有 JSON 载荷中记录发布前快照 envelope 和证据 envelope。调度在全局变更锁内复核请求主体及 lineage，再保存制品、Prepared 任务，最后安装证据、保存玩家引用并标记 Ready。任务持久化后发生任何失败均保留恢复依据；未成功入队的孤立制品由下一次同键调度替换，或由制品清理回收。清理也使用同一全局锁，避免删除正在调度但尚未入队的制品。
- 恢复只允许目标仍为原基线，或已是本次完整证据版本；版本比较包含身份、原始/载荷哈希和下一代 lineage token。恢复读取当前任务状态，拒绝证据与任务/袭击主体绑定不符或载荷校验失败；过时扫描不会重置 Ready、人工审核状态或重建已移除任务。重复调度须匹配原证据及结算来源/客户端结果，冲突请求不能触发原任务恢复。
- 旧任务缺少发布前基线时，只自动完成“证据已完整安装”的引用修复与 Ready 转换；其他状态保留任务和证据并报告冲突，沿用后台有限重试后转人工审核的机制，不猜测原快照。该变化不修改协议 DTO、数据库表或冻结的 1.6 文件。

## 续修：事件失败报告的身份、来源和终态边界

- `ReportEventApplicationFailure` 原先允许事件任意一方报告，非交易分支还会直接把客户端提供的 `SourceEventId` 标记失败；已入档、取消或拒绝的根事件也可能被改写。重复 Failed/Conflict 分支跳过通知，账本成功后、唤醒前中断会丢失即时通知。交易失败处理另会把已经入档的交换改成 Failed/Conflict，破坏原扣款或自提交换证据。

## 续修：直接完成交易入口的履约证据约束

- 原 `CompleteTradeOrder` 与取消共用通用关闭函数，卖家只需给出订单身份就能把未履约订单和备忘标为 AppliedToSnapshot；已完成分支也不检查交换/交付证据，并因只找活跃备忘而遗漏通知。旧实现负向测试明确复现 `completion bypassed snapshot fulfillment: Recorded`。

## 续修：履约失败只补偿经过关联校验的交易

- 原失败处理按订单 ID 和交付键前缀收集事件，未核对唯一交换及交付双方/载荷；卖家旧返还只取前缀匹配的第一条，买家已有返还则重新构造为待交付状态。新增取消接单回执也会被当作普通关联交易改成 Failed，破坏原回执。旧实现负向验证分别复现回执被改写、已消费返还状态被重置、错误交换接收者被接受，以及任意旧返还后缀被接受。
- 新增 `TradeFailureGraph`：先验证唯一交换、订单货物/费用/履约方式、备忘身份及引用、准确的双方交付键/物品/用途，再决定补偿范围。普通礼物即使使用相似键也不加入交易；取消接单回执不属于需要关闭的交付集合。已自提入档或任一交付已入档时保留原证据、转入冲突，不自动退款。付款补偿要求交换具有已入档状态、快照 ID、时间和成功标记；不根据孤立的状态值推断买家已付款。
- 卖家返还仅接受标准键，或后缀准确引用该交易交换/交付事件的旧键，且全局最多一份；不再按目标玩家筛选后取第一份。买家返还必须准确绑定唯一交换。两种返还都核对完整身份、物品、用途和可用状态，卖家落点匹配原订单；已有返还按原记录保留，包括旧 ID、已消费状态及买家当时的落点。与其他撤单原因的返还并存时拒绝猜测。

## 续修：运输舱赠送迁移至快照事务

- 运输舱到达原先直接调用无快照的 JSON 礼物入口，发送方货物移除没有与服务端礼物共同提交。现改为复用商队赠送的 `StartSubmitRemovedGift` 流程：打包货物移除后的快照，通过认证的 multipart 礼物入口提交，成功后更新本地 lineage；失败保留未确认事务和重试窗口，提交重试沿用原快照、载荷和幂等键。普通赠送与强制投递共用该路径。
- 不能在到达回调中立即保存游戏。本机 1.7.4979 rev109 的 `Assembly-CSharp.dll`（SHA256 `a97a01c4319414414c0ca39f3565215e83300dc608dc94b69a27720095b4e751`）静态 IL 显示：引擎先设置 arrived 标记并调用到达动作，回调返回后才清空运输舱列表并销毁世界对象。到达动作同步占用本地变更边界、复制货物容器引用，主线程下一次处理队列时再提取物品和打包快照。准备失败保留容器供重试，不把引擎随后清空的原列表用于延迟读取。
