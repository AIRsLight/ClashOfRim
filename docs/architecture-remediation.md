## 缺陷依据与设计约束

### 1 行为测试未进入发布门槛

`.github/workflows/release.yml` 原流程只构建与验证包。现有 Client、Save、Events 均为控制台测试程序，必须用 `dotnet run` 执行，不能用返回成功但不执行这些用例的 `dotnet test` 替代。客户端完整测试必须使用本地游戏运行库；NuGet 中的引用程序集不能执行游戏代码。

### 2 会话生命周期

`ClashOfRimMod.SessionRuntime.cs` 的普通后台刷新未统一绑定取消与代次。退出会清空集合，但旧响应随后仍可调用 `CaptureWorldMapMarkers`、`MergeChatMessages`；主线程动作也可能跨游戏实例执行。已有重连安全策略保留，新增会话所有权应覆盖结果应用与 finally 清理，防止旧请求清除新请求的运行标记。

### 3 跨存储提交

`RepayBankLoanWithSnapshot` 先 `ReceiveSnapshot`，后 `MarkRepaidWithSnapshot`。文件原子替换只保证快照文件完整，不保证与 SQLite 业务记录共同提交。中途崩溃可能留下扣钱快照和未还贷款。待确认恢复只处理已有 Pending 记录，不能推导未持久化的业务意图。改造必须有持久化意图或共同事务边界；不能只加进程内锁。

### 4 快照锁范围

`ReceiveSnapshot` 在 `RaidSettlementSnapshotMutationGate` 内执行解压、哈希、XML 索引和存储。优化必须保留提交时的连续性、lineage 和袭击结算互斥检查；不能只将原调用移出锁。存储层共用锁也需要单独评估。

### 5 职责边界

`ClashOfRimMod` 的 partial 文件共享会话、经济、世界、聊天和 UI 状态。`ClashOfRimNetworkState` 是全量依赖集合，端点直接编排持久化。优先抽出前述修复需要的真实服务，避免只重命名或移动文件。远程地图投影中的 Scribe、Current.Game 和反射调用应有独立的游戏运行时入口。

### 6 协议重复

`ClashOfRimModNetworkClient` 手写路由，`ClientNetwork/Dtos` 与 `ClashOfRim.Protocol` 同时定义传输模型。先共享路由；DTO 迁移必须保持现有 JSON 字段、枚举、可选值、默认值兼容，并以两端实际序列化器验证。1.6 冻结客户端不重新编译。

## 续修：礼物快照与事件共同恢复

首轮改动已提交为 `df3d4bfa`。本步继续解决问题 3，范围为 `CreateGiftWithSnapshot`。

- 原流程在发布扣除物品后的快照之后才保存物品包和投递事件。现改为：准备快照 → 锁内重验 lineage 与幂等键 → 持久化物品包 → 固定礼物事件 → 写入提交意图 → 发布快照 → 追加事件 → 通知及后处理 → 删除意图。写入意图之前失败可能遗留未引用物品包，但不会发布扣物品快照。物品包使用每次提交独立的命名空间，避免失败尝试复用其他请求的包。
- `BankSnapshotCommitService` 扩展为 `SnapshotCommitService`，银行与礼物共用恢复入口及快照冲突检查。礼物日志保存稳定的事件 ID、双方身份、物品来源与接收方式；恢复使用原事件，不重算当前配置。事件已追加但通知失败时，恢复再次唤醒接收者，不新增投递事件。
- 重试必须匹配发送者、殖民地、确认快照、礼物业务类型和接收者；认证主体必须匹配请求发送者。提交锁内再次检查重复请求。较新快照或已被其他事件占用的幂等键会阻止恢复，日志保留供排查。
- 为读取既有未完成银行日志，继续使用数据目录 `bank-snapshot-commits/`。银行记录仍使用格式 1，礼物使用格式 2；数据版本 9→10 要求服务端支持礼物恢复。备份仍需包含该日志目录、SQLite、快照及物品包；后处理器仍须幂等。
- 新增 7 个故障/冲突场景，使用真实 SQLite、快照文件并重新打开存储：快照前、快照后、事件写入、通知、后处理失败，以及较新快照和幂等键冲突。旧银行格式缺少 `Gift` 字段的日志也纳入恢复测试。
- 新增礼物端点测试，直接调用端点并执行真实 multipart 解析和认证，覆盖成功、重复、错误接收者、错误发送者、身份冒用及无效载荷；这不等同于通过 Kestrel 的 HTTP 集成测试或双客户端实机测试。
- 验证：`Tools/Test-Regression.ps1` 通过（Events 50 项、Save 75 项、Client.Core 5 组及 NetworkSmoke 独立管线场景）；`Test-FrozenLegacy.ps1` 确认 77 个冻结文件未变。本步只改服务端和测试，未重新进行完整客户端运行库测试及双客户端实机测试。

## 续修：交易所需的账本原子批量提交

- `IAuthoritativeEventLedger.ApplyBatch` 将新增事件与既有事件状态变更作为一批处理。SQLite 使用单个事务，文件账本先持久化完整候选集合再发布缓存，内存账本在同一锁内检查并应用；文件及内存账本其他公开操作也使用同一锁。
- 状态变更携带预期旧状态。已经关闭订单的新成交批次会被拒绝；只有整批事件已存在时，才允许按既有完成状态重试。重试保留投递事件后续的消费状态，不将其恢复为待投递。
- 新增三个账本实现的验证失败、SQL 中断回滚、文件保存失败缓存隔离、持久化重开、重复执行及并发买家竞争测试。本步骤提供基础能力；交易端点接入提交日志另作下一步，尚不能据此认定交易跨快照恢复完成。
- 验证：`Tools/Test-Regression.ps1` 通过（Events 51 项、Save 75 项、Client.Core 5 组及 NetworkSmoke 独立管线）；全部 77 个 1.6 冻结文件哈希保持不变。

## 续修：交易成就后处理可恢复

交易快照接入已提交为 `efdb6e8b`。本步修复上述成就后处理缺陷：

## 续修：文件包读取解压移出锁及历史一致性

- `FileColonySnapshotIndexStore.GetLatestPackage` 在共享锁内捕获最新元数据和对应压缩文件字节，随后在锁外读取包结构、解压载荷和重建索引。读取返回调用期间捕获的一份完整版本，不承诺返回时仍为最新；不会在解析完成后重新发布缓存。物理文件读取仍在锁内，压缩文件缓冲会增加单次读取的短期内存占用。未保留打开的磁盘句柄，避免 Windows delete-pending 状态阻碍同路径重建。
- 两种 `StoreLatest` 将历史哈希的复制、追加、持久化与缓存发布放在同一临界区，修复并发写入丢失先前已接受哈希的问题。`RemoveLatest` 先完成文件删除再移除缓存，删除失败不会让当前进程与磁盘状态分叉。
- 调用方审计同时发现下载附带战场清理直接写回捕获的旧包。现在有战场数据的清理入口先取得全局变更锁并恢复提交，再核对当前快照身份、内容哈希及下一代 lineage token；不匹配或殖民地已删除时只返回已捕获的读取结果，不写回或生成损失事件。这个检查不等于清理的快照/账本已共同提交，剩余窗口已加入上述优先顺序。
- 新增确定性暂停索引扩展的测试，覆盖 raw/gzip 两种载荷：解析暂停时其他殖民地写入和同殖民地替换、删除、重建均可完成；旧读取保持原载荷/身份且不复活旧缓存。另覆盖并发两种发布接口的完整历史、并行读取一致性、缺失/损坏/仅元数据包、重开存储，以及 Windows 文件共享冲突导致发布/删除失败后的缓存与重试。下载清理验证当前版本正常清理及快照 ID、哈希、token、删除状态四种失效基线。
- 读写混合探针增加 `--with-downloads`：每轮每个殖民地同时发起上传和最新包元数据下载，后者实际触发服务端文件包重建，并校验返回的元数据对应旧版或新版完整快照。测量方法与结果见 [锁测量记录](snapshot-mutation-metrics.md)。
- 最终同条件复测中，706207 字节、8 并发的提交等待 p95 从 428.67 ms 降至 57.58 ms，持锁 p95 从 276.45 ms 降至 45.48 ms；串行上传未见稳定改善，不据此承诺生产吞吐。默认可移植回归通过（Events 51 项、Save 87 项、Client.Core 5 组及完整 NetworkSmoke），全部 77 个 1.6 冻结文件不变。

## 续修：袭击证据发布意图与冲突恢复

- 原 `Prepared` 恢复只比较证据快照 ID，不同就直接安装证据，可能覆盖较新存档或复活已删除殖民地；写文件抛错时还可能删除已持久化任务和证据，丢失“文件实际已发布但调用失败”的恢复依据。
- 新任务在原有 JSON 载荷中记录发布前快照 envelope 和证据 envelope。调度在全局变更锁内复核请求主体及 lineage，再保存制品、Prepared 任务，最后安装证据、保存玩家引用并标记 Ready。任务持久化后发生任何失败均保留恢复依据；未成功入队的孤立制品由下一次同键调度替换，或由制品清理回收。清理也使用同一全局锁，避免删除正在调度但尚未入队的制品。
- 恢复只允许目标仍为原基线，或已是本次完整证据版本；版本比较包含身份、原始/载荷哈希和下一代 lineage token。恢复读取当前任务状态，拒绝证据与任务/袭击主体绑定不符或载荷校验失败；过时扫描不会重置 Ready、人工审核状态或重建已移除任务。重复调度须匹配原证据及结算来源/客户端结果，冲突请求不能触发原任务恢复。
- 旧任务缺少发布前基线时，只自动完成“证据已完整安装”的引用修复与 Ready 转换；其他状态保留任务和证据并报告冲突，沿用后台有限重试后转人工审核的机制，不猜测原快照。该变化不修改协议 DTO、数据库表或冻结的 1.6 文件。
- 新增真实文件制品/快照及 SQLite 任务/玩家注册表回归：发布前后中断、Prepared/Ready SQL 失败、玩家引用 SQL 失败、同进程/重开恢复、四个并发调度、重复参数冲突、新快照/删除/同 ID 不同哈希或 token、制品缺失/绑定冲突、旧载荷恢复和过时扫描。默认完整回归通过（Events 51 项、Save 88 项、Client.Core 5 组及完整 NetworkSmoke），77 个 1.6 冻结文件不变。
- 本步只覆盖进攻方证据发布。守方结算快照与账本仍有分步写入窗口，下载/超时清理与损失通知也尚未共同恢复；下一步先处理守方结算，再处理清理。双客户端实机验证继续保留待办，远程环境的窗口输入限制未解除。

## 续修：守方结算快照、玩家引用与账本共同恢复

- 原执行器先写结算事件，再发布守方快照及逐项更新源袭击状态。中断可能留下无对应存档的结算事件；旧恢复分支还仅凭 `PreviousSnapshotId` 判断新存档已经结算，无法证明应用的是本次损失。
- `RaidSettlementLedgerRecorder.CreateSettlementEvent` 只构造候选事件。执行器在锁外计算差异和编辑快照，提交锁内恢复已有意图，重新核对源袭击的主体、载荷和地图，以及守方快照身份、双哈希、lineage token。投递状态可以继续前进；准备期间目标或存档变化则拒绝发布。
- 新增提交日志格式 8，固定原守方 envelope、完整编辑后快照、源袭击、结算事件和时间。先持久化意图，再发布快照、保存玩家引用、原子写入结算账本批次并唤醒目标用户，最后删除日志。启动、请求和后台结算共用恢复入口。中断重放使用日志中的字节和 token，不重新计算损失；冲突保留日志并拒绝覆盖。该服务端编辑不运行普通上传后处理，也不确认守方其他待确认业务。
- `LedgerBatch` 增加带完整预期源事件的应用变更。内存和文件账本先构造完整候选；文件保存成功后才发布缓存。SQLite 在同一事务中插入结算事件并写入源袭击的投递/应用快照、时间和结果，后者失败会回滚前者。重放保留结算事件后来的投递/应用状态，已有投递引用也不会被基线替换。
- 移除凭父快照 ID 猜测完成的恢复分支。没有提交日志的旧半提交进入人工审核，不自动再扣一次损失或把任意子快照当作结算结果。数据库版本升至 17（无表布局变化），阻止不理解格式 8 的旧服务端打开当前数据；日志目录和备份范围保持不变。
- 新增真实文件与 SQLite 中断回归，覆盖发布前后、玩家引用、结算事件插入、源事件更新、通知唤醒，同进程和重开恢复，较新/删除/同 ID 不同哈希或 token、源事件/幂等键冲突、后续事件状态、四个并发结算和准备期间状态变化。三种账本均验证原子应用与重复批次；Windows 额外验证文件替换失败不污染缓存。默认完整回归通过（Events 51 项、Save 89 项、Client.Core 5 组及完整 NetworkSmoke），全部 77 个 1.6 冻结文件不变。
- 下一步处理下载和超时战场清理的快照/损失通知共同恢复，再继续锁职责与 DTO 收敛。双客户端实机验证仍待可交互桌面环境，不以服务端回归替代。

## 续修：战场清理快照与损失通知共同恢复

- 下载附带清理和超时清理原先先发布删去战场的存档，再逐条写攻击方损失、支援归还通知及支援失败状态。发布后中断会失去生成通知所需的地图/Pawn 证据。现先纯构造清理事件批次，再写提交日志格式 9，保存原快照基线、完整清理后存档、源袭击和支援事件及固定损失批次。
- 发布顺序为持久化意图、快照、玩家引用、账本批次和通知唤醒，最后移除日志。支援归还通知与原支援的 Failed 状态在同一账本批次中应用；任何写入或唤醒失败均保留意图。恢复校验原快照/本次已发布版本及源事件，不重新扫描地图，不重算通知，不重置通知后续的投递/应用状态。
- 两个清理入口核对快照所有者与源袭击，并要求所有待清理战场均绑定同一袭击且该攻击者没有活动袭击。旧超时任务不能清掉新战场或其他玩家地图。下载的捕获基线另补载荷哈希检查。编辑准备失败仍可保留原读取结果；开始提交后的错误向上传播，避免已经部分发布时仍返回成功的旧下载结果。
